## Design decisions

- Integration surface: project-scoped custom tool `.opencode/tools/deepseek_delegate.ts` (+ companion exports for background output/cancel).
- DSH runtime path: hardcode launch against the checkout's built runtime demo bin OR a TS client that spawns it. A small **node helper bridge** (spawn runtime, speak JSON-RPC, normalize result) is the "SDK wrapper boundary" since Python SDK is not installable today.
- The runtime bin lives under `/Users/liuzy/deepseek-harness` (external repo). Tool must resolve runtime bin path robustly (env override `DSH_RUNTIME_BIN` + default).
- Presets: explore(read-only, v4-flash), write(workspace-write, v4-flash, context packet), vision(vision-exp, image content blocks, optional workspace-write), unrestricted(danger-full-access + exact token).
- v1 network caveat must be surfaced. No hard network block in v1.

## Schema todo (2, 2026-09-04) — zod 4.1.8 verified API facts
- **`.superRefine` exists on classic schemas** (`z.object(...).superRefine((data, ctx) => ...)`) and returns `this`, so `z.infer` keeps the object shape. Inside it, `ctx.addIssue({ code: "custom", path, message })` — `code: "custom"` is REQUIRED (custom issues are `$ZodIssueCustom`). The refinement ctx type is NOT exported as `z.RefinementCtx` in v4; don't annotate ctx params, rely on contextual typing (or a narrow structural helper type).
- **Unknown-key rejection**: v4 `z.object().strict()` works but the d.ts steers you to `z.strictObject({...})` — use that for the input schema so arbitrary `model`/`provider` keys become `Unrecognized key` issues. superRefine does NOT run when the base object parse already failed.
- **ISO datetime**: v4 deprecated `z.string().datetime()` in favor of `z.iso.datetime()` (no `{ offset }` param in 4.1.8 — params are `pattern`/`when`/error only). `new Date().toISOString()` (Z-suffixed) passes as-is; non-ISO strings reject.
- **Positive ints**: `z.number().int().positive().optional()` is the pattern for `max_tokens`/`timeout_ms`/`pid`.
- **Matrix via switch in superRefine, not per-field**: field-level schemas can't express "permission X forbidden for preset Y" or "images only under vision"; a single switch on `preset` adding issues with `path` (e.g. `["permission_mode"]`) keeps failure messages field-targeted.
- **Context packet field kinds** (spec-exact): only `relevant_paths` and `verification_commands` are arrays; `objective` is the only required field at schema level (richness gating of write packets belongs to the todo-6 builder); `expected_changes` is a STRING, not an array.
- `tsconfig.json` includes only `.opencode/tools/**` + `tests/**`; `src/schema.ts` is still type-checked because imported files join the tsc program — no tsconfig edit needed (verified exit 0).
- Evidence workflow: tests stay pure; evidence JSON generated by a throwaway script (imports `src/schema.ts` by absolute path from the repo, so `zod` resolves via repo node_modules) run with `bun`.

## Background job lifecycle gotchas (todo 8, 2026-09-04) — src/jobs.ts
- **Bun.spawn has NO `detached` option; use `node:child_process` spawn** (bun implements it fully — probe-verified under bun 1.3.11: `spawn` event fires, detached child becomes its own process-group leader, `process.kill(-pid, SIGTERM)` delivers group-wide, exit event reports `code=null signalCode='SIGTERM'`). Detached is REQUIRED for safe group-kill: a non-detached child shares OUR process group, so `kill(-pid)` would signal the opencode/test process itself. Redirect child stdout/stderr by passing parent-side `openSync(path,'a')` fds via `stdio: ['ignore', outFd, errFd]` (files exist from spawn time; no pipe buffering; no EPIPE when the parent dies). Do NOT close parent fds until the child's exit event.
- **Bun types `process.kill(pid, 0)` as returning literal `true`** — `result !== false` / `result === false` comparisons are TS2367 'no overlap'. Write alive-checks as try/process.kill(pid,0)/catch-ESRCH only; bun throws ESRCH like node (verified), so `pidGone = try kill -> false, catch -> code==='ESRCH'`.
- **Job file write ordering is safe because 'exit' is a macrotask**: spawn → await `spawn` event (microtask continuation) → persist the `running` record with pid → attach the exit listener → (fallback) if `exitCode`/`signalCode` already set, run the monitor manually. All sync, so the running record is on disk before any exit event can be observed; the monitor's terminal persist is ALSO synchronous inside the exit handler, which makes the cancel-vs-exit race resolvable by a simple file re-read instead of locks.
- **Cancel must set an in-process `cancelled` flag synchronously BEFORE signaling** so the exit monitor never overwrites the terminal write, and must re-read the job file after the kill ladder and only persist `cancelled` when the file still says `running` (a natural exit that won the race leaves its `completed`/`error` record intact). Grace ladder mirrors the DSH shutdown ladder: group SIGTERM → wait `cancelGraceMs` (default 1500) → group SIGKILL → confirm ≤1500 ms, else JobError CANCEL_FAILED. cancel() waits for actual death (child exitCode/signalCode or pid ESRCH) before returning, so a resolved cancel() implies a reaped child.
- **SIGTERM semantics differ between the runner and stubs**: delegate-runner traps SIGTERM, closes the harness, and exits 1 (no stdout line) → tracked exit has `exitCode=1`; a stub with default disposition dies by signal → `code=null signalCode='SIGTERM'`. A cancel test that must exercise the SIGKILL escalation needs a stub that installs a SIGTERM handler and keeps running (`process.on('SIGTERM', ...)` + `setInterval`). Marker assertions on kill-race writes can flake: a SIGKILL can interrupt the handler's writeSync mid-syscall (observed 39/51 bytes in .err) — keep assertion strings short and/or lengthen cancelGraceMs for evidence runs.
- **Runner result line → DelegateOutput normalization**: the `.out` file is read for its LAST non-empty line (seek-from-end read capped at 4 MiB, first chunk dropped when truncated) and parsed into the runner's `{ok:true, session_id, final_response, finish_reason, events_len}` / `{ok:false, error:{code,message}}` contract; `ok:true` requires exit 0 (or unknown exit info during lazy settle) → `completed`, else `error` with the wire code (RUNNER_EXIT/NO_OUTPUT/SIGNAL when the line is missing/malformed). Every constructed record AND every served output view is safeParse'd through delegateJobSchema / deepseekDelegateOutputSchema before persistence/return — a schema failure is a structured JobError, never a torn file.
- **Atomic-ish writes = temp + rename in the SAME directory** (`<file>.tmp-<pid>-<hex>` → renameSync), atomic on POSIX; readers validate through the schema anyway. Tail reads of `.out`/`.err` are capped (200 lines / 64 KiB, redacted via runner-lib's redactSecrets + literal DEEPSEEK_API_KEY) so a chatty child can't balloon a tool response; error messages embed at most an 800-char stderr tail.
- **Job ids are `bg_<12 hex>`** (minted with randomBytes, collision-retried) and every public entry validates `/^bg_[a-zA-Z0-9]{8,64}$/` BEFORE touching the filesystem — model-supplied job ids can never escape the jobs dir (`../` or `bg_short` → JobError JOB_INVALID). Lazily settling orphaned jobs: `status()`/`output()` on a `running` file whose pid is gone and which has no in-process monitor (parent restarted mid-job) reconstructs the terminal record from `.out` once; detached children survive the parent, so cross-restart output works.
- **Evidence**: `.omo/evidence/deepseek-delegation-tool/task-8-happy.json` (stub completed → normalized DelegateOutput w/ session_id/final_response/finish_reason; job file schema-conformant) + `task-8-failure.json` (SIGTERM-ignoring stub cancelled via escalation, pid dead via kill(pid,0) ESRCH with retry window, .out/.err captured, double-cancel rejects JOB_NOT_RUNNING). ## Vision input admission gotchas (todo 9, 2026-09-04) — src/vision.ts
- **Resolved content-block shape** (investigated end-to-end across llm/llm-deepseek + sdk/protocol + sdk/server + attachment/attachment-local + acp): the SDK JSON-RPC `session/prompt` wire carries `contentBlocks: ContentBlock[]` (`@deepseek-ai/dsh-llm`). The image block is `{ type: 'image', attachment: ImageAttachmentRef }` where `ImageAttachmentRef` (`@deepseek-ai/dsh-attachment` types.ts:11-32) = `{ attachmentId: string, mediaType: 'image/png'|'image/jpeg'|'image/webp'|'image/gif', bytes: number, width: number, height: number, name?: string }`. There is NO base64/data-url field on the SDK wire — unlike ACP which accepts `{type:'image', data:<base64>, mimeType}` and converts it in-process via `attachments.saveImages` → ref blocks (base64 discarded after admission).
- **sdk-jsonrpc-server forwards verbatim, zero validation**: `prompt()` (server.ts:132-143) does `createUserMessage({ content: params.contentBlocks, source: {kind:'user'} })` → `deepFreeze(structuredClone(message))` → `agent.followup(message)`. No whitelist, no type-tag check, no image-modality check, no base64 decoding, no persistence. `handleRequest` just casts `params as unknown as SessionPromptParams`. So the block JSON you send IS the message content, but the block must be well-formed for the deeper session/llm path.
- **attachmentId = sha256 of NORMALIZED bytes, NOT raw input** (attachment-local/src/store.ts:102 `const sha256 = digest(normalized.data)`; line 79 docstring: "Deterministic normalized bytes whose digest is ref.attachmentId"). The store's `saveImages(inputs: SaveImageAttachment[])` (index.ts:189) takes raw `{data, mediaType}`, decodes→scales→re-encodes (normalization.ts), then computes sha256 over the normalized result. So an out-of-process bridge CANNOT compute the correct attachmentId without an image library (forbidden by this todo) — `buildImageContentBlocks` computes sha256 of raw bytes as a best-effort content-addressed id; for tiny images already within budget (no scaling, same encoder) raw and normalized may coincide, but for general images the id will NOT match and the adapter will fail to resolve the image via `ctx.attachments.readImage(ref)`.
- **No image-upload RPC on the SDK wire**: the protocol has exactly 3 methods (initialize, session/prompt, shutdown — protocol/types.ts:100-105). `saveImages`/`readImage` are in-process `LocalAttachmentStore` methods (attachment-local/src/index.ts:134-250), unreachable from an out-of-process JSON-RPC caller. The store is disk-backed under `this.root` (`objects/<sha256[:2]>/<sha256>` layout, store.ts:39-40), so a bridge that controls `$DSH_HOME` could in principle write normalized bytes directly — but computing normalized bytes requires the store's own decode/scale/re-encode pipeline (normalization.ts), which needs an image codec. This is the documented residual risk: the block SHAPE is correct and type-complete; end-to-end delivery additionally requires a registration channel the SDK wire does not provide (in-process saveImages, a read_image tool, or direct disk writes with pre-normalized bytes).
- **Admission limits** (attachment-local/src/index.ts:28-48): DEFAULT_MAX_IMAGES_PER_MESSAGE=20, DEFAULT_MAX_MESSAGE_IMAGE_BYTES=200MiB, DEFAULT_MAX_IMAGE_BYTES=20MiB per source, DEFAULT_MAX_IMAGE_DIMENSION=8192px, DEFAULT_NORMALIZED_IMAGE_MAX_DIMENSION=2048, DEFAULT_NORMALIZED_IMAGE_MAX_BYTES=4MiB. These match the llm-deepseek README and the inherited wisdom notes. The probe does NOT enforce these (it's a pre-admission gate; the runtime enforces at saveImages time) — but the audit metadata captures per-image bytes so T10 can flag over-budget inputs.
- **probeImage design**: stat (must exist, be a regular file, nonzero size) → extension allowlist (png/jpg/jpeg/webp/gif) → magic-byte sniff (read first 12 bytes; PNG 89504e47..., JPEG ffd8ff, GIF "GIF8", WebP "RIFF"+"WEBP"@8). Extension drives eligibility; magic verifies content. Mismatch (e.g. .png file with GIF bytes) → `IMAGE_MAGIC_MISMATCH` (reject, don't reclassify — audit trail must reflect true input). .jpg and .jpeg are treated as equivalent (both map to the jpeg signature). No image-processing dep — `node:crypto` for sha256, `node:fs` openSync/readSync/closeSync for magic + full-byte read.
- **resolveVisionInput rejects duplicates** by resolved absolute path (`DUPLICATE_IMAGE`): sending the same attachment twice is wasteful and the audit trail should reflect unique inputs; the caller (tool layer) is responsible for deduplication. Input order is preserved. Relative paths resolved against `cwd` via `path.resolve`.
- **Permission gating**: schema (todo 2) already rejects `danger-full-access` for vision via superRefine; `assertVisionPermissionAllowed(mode)` is a defense-in-depth runtime guard that also rejects it. `requiresWritePermission(mode)` returns true only for `workspace-write` (vision defaults to read-only; write is opt-in). `buildVisionAuditMetadata(images, mode)` returns `{ images: [{path,bytes,ext,mimeGuess}], writeRequested }` for T10 consumption.
